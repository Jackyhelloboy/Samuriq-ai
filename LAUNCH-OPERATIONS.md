# Production operations update

Production no longer serves demo workspaces or layout-preview projects. Old demo routes redirect to the real project board; no fake contributors or follow-ups are inserted. Real registration, historical agreements and financial data remain retained.

The workspace switcher is an explicit, authenticated server action. A selected view is a navigation preference, never an authorization grant. Contributor-selected Support and Notifications use the contributor layout and scoped records. Owner/manager server checks remain independent of the view cookie. The owner/manager client compatibility page is separate from the contributor's gated, one-use launch route.

Add Payments replaces the contributor payment-section label. Public page copy points to accepted settlement terms, while previously accepted policies and ledger mechanics are preserved. The owner can publish an audited, safely rendered public privacy notice and prospective role/project agreements from the policy panel. Historical receipts remain immutable.

Handles accept 3–30 lower-case letters, digits, dots and underscores, beginning/ending with a letter or digit. A database unique index resolves concurrent collisions; existing profiles receive stable member handles without changing their legal names or payment identities. The folder guide recommends these handles; existing Drive folders are not renamed automatically.

Contributors submit encrypted PNG/JPEG/WebP screenshots through a scoped, same-origin route, with streaming request limits, an 8MB file limit and a 60/hour per-account/project attempt cap. A SHA256 index atomically rejects byte-identical reuse within the project. A partial unique index rejects a second non-rejected completion/session ID for the same contributor. Corrected proofs retain the earlier rejected record. No screenshot URL is public. Contributors can read their own evidence; current assigned reviewers and authorized staff can inspect it. Review decisions are version-checked, audited, and locked once a day enters QC reconciliation. Flagged items open a private management ticket. A flagged image is a concern, not proof of fraud. Edited or different copies can evade an exact hash, so reviewers still inspect content and the client remains the source of QC.

The Hindi project now requires checked uploaded evidence from both permanent partners for every listed section before a worked-day TL record can be saved. Counts must match checked uploads. Existing records are retained. Client-required Drive copies still need upload to each person's restricted Drive folder. Automatic Google Drive permission checks, folder renaming and file synchronization are not connected; do not claim otherwise.

Each team has a per-member daily contact log with method, outcome, note, next action, actor and timestamp. TL daily contact totals are derived from unique members in that log, not arbitrary input fields. Logs are staff-entered statements, not automatic proof of calls or client activity. Client recording telemetry and client QC cannot be read without client support.

Telegram's linked community cannot be converted by unlinking the announcements channel in this run: automatic approval review rejected that action because existing comments/discussion access could be disrupted. The existing linkage was preserved. The owner phone was already hidden (Nobody), with phone discovery limited to contacts. Profile display name and bio were updated to Samuriq AI project coordination, and the existing company mark was uploaded. Bot creation/configuration and real client tutorial media remain prerequisites; no bot notifications, real client login/recording or payouts are represented as tested.

- Login clears previous workspace selection. Dropdowns affect navigation only; server permissions remain authoritative.
- Four owner-requested temporary review accounts expire on 14 November 2026 at 15:27 UTC. Passwords are random and only salted PBKDF2 hashes are stored. The existing owner remains the only admin. Review TL/helper/contributor assignments use an archived, non-public access-review project; no recordings, financial records, bank details or client approvals are fabricated. The manager review account is a real manager and should be kept private. Review logins are separate from the normal company accounts and do not auto-accept any agreement.
- Archived projects are excluded from public listings and blocked in detail, onboarding, application and client-launch access.
- Telegram linking uses a short-lived hashed one-use website code, not a matching Telegram username. Webhook secrets are checked and code claims are atomic. Existing legacy username links are not used for reminders. `BOT_USERNAME`, `BOT_TOKEN`, and `TELEGRAM_WEBHOOK_SECRET` must be configured before bot notifications are live. The owner-requested @SamuriqAIProjectAssistBot was created and its token is stored as a private runtime secret. Setup validates the bot identity, applies its profile/commands and registers a fixed HTTPS webhook using a secret header; setup is idempotent with a five-minute failure lease. No group admin rights are granted.
- Telegram announcements were unlinked as authorized. The community now has Hindi, Telugu, Guidance and Support topics; members cannot create additional topics. Company branding was applied to the community and all three project channels.
- Client tutorial media is still needed from management. Gating is not bypassed to make a project appear launch-ready. The client platform may block framing and cannot be monitored internally or restricted to Samuriq-only registration without client cooperation.
- The Telegram reminder action uses actual pair review records for evidence projects, excludes archived/restricted work and groups TL notices strictly through current team assignments. It ignores legacy username-only links, limits each request to 50 delivery attempts, keeps a per-recipient/project/day success receipt, and leases failed attempts for five minutes to avoid concurrent retries. The owner’s existing Send reminders action triggers it; no new unattended messaging schedule was enabled.

## Registration, access and India coverage repair (13 November 2026)

Production errors were traced to throttled sign-in actions and project enrollment checks after profile saving. Expected limits now return clear recovery messages, submit buttons disable while pending, and profile saving redirects to a permission/role-change explanation when required. Archived memberships no longer block new applications. Project and return destinations are preserved through sign-in. Existing account/profile data and role restrictions are retained.

Email collision triggers prevent new case-insensitive duplicate account emails without deleting existing accounts or preventing same-account password updates. View guards direct unassigned users to an access-denied page; mutation guards still reject unauthorized operations. Identity/staff lookups are memoized within the React request, not shared across users.

Profile and public India selectors include 36 states/union territories, city suggestions derived from 5,050 upstream LGD urban-local-body records, all Eighth Schedule language options, English and regional suggestions. Custom town/language entry remains available. City files load by selected state. Existing location strings remain unchanged unless edited. Source snapshot and MIT attribution are in public/data/india.

Client workspace discovery includes published projects even before application, confirmed partner applications, and explicit missing-training notices. Work approval, pair confirmation and tutorial gates are unchanged. Staff and approved contributors can request a cached connection/header check; it never returns the client URL publicly or claims to verify work. Server checks are restricted to CLIENT_HEALTH_ALLOWED_HOSTS (default webrtcsg.shenfei-rec.com), validate redirects, reject private/credentialed URLs and cache results for ten minutes. Independent browser checks confirmed that the client sign-in screen loads directly and inside an isolated development iframe; no client account was created, signed in or used to record. Temporary compatibility pages were removed before publication.

Validation includes registration/role/evidence regression suites, a canonical-page audit, frame-policy tests, and desktop plus 390-pixel mobile browser layout checks. These checks are not a production capacity guarantee or a guarantee that every future client platform permits embedding.

Dependency hardening: Next and its ESLint configuration are aligned at 16.4.6; Zod is upgraded to 4.6.7-compatible releases, with patched sharp, source-map-js, fast-uri and baseline-browser-mapping resolutions. `npm audit --omit=dev` reports zero advisories after installation. Type checking, the production build and role/security regressions are rerun against the updated lockfile.

The top-level cross-origin write guard drains declared small form bodies (up to 8 KiB) before rejecting them. This retains CSRF rejection and avoids a reproducible local Worker stall on the next request; large/unknown request streams are not parsed by that guard. The launch regression explicitly sends a rejected cross-origin request followed by another approved work-desk request.

Exactly one real project remains active at release: speech-pair. Three explicitly labeled sample projects are listed as closed, accept no applications, have no client destinations, and are forced closed by project state logic. No fake contributors, work records or payments are added. Existing project/member data is preserved. Active projects sort first.

Telegram ownership is verified by the existing bot's secret-validated private webhook, one-use 10-minute connection link, actual sender/chat identity and actual Telegram username. One Telegram identity cannot bind different website accounts, enforced by database triggers. The authenticated self-status endpoint never returns chat IDs. The page checks every ten seconds only while visible, stops after ten minutes, and checks immediately when returning from the Telegram app. The required project's training/actions and client access recheck verified username server-side; community membership and TL approval remain separate. Typed profile names do not overwrite an already verified Telegram username. The guide shows Android Settings / Edit profile → Username. Existing users must complete verification before this project's work access.

The user-supplied Drive sample video is configured and explicitly labeled reference material, not client-issued training. Browser QA confirmed the Drive preview player and client public sign-in render inside a 390px development viewport; no client sign-in, recording or QC was performed. Drive does not expose trusted playback telemetry here: coordinator verification remains required and cannot be silently bypassed. Real client instructions still need management confirmation. Temporary compatibility pages are removed from the published source.

Android layouts use large inputs, a bottom navigation bar, quick work/evidence/Telegram/help actions, simplified project browsing and an active-first list. The client desk provides expanded view (with a CSS fallback if fullscreen is unavailable) and a 960px horizontally scrollable wide layout. This does not change or proxy the client's independent website; microphone/login compatibility remains dependent on the client and browser. Bank and staff permissions are retained.
